Surface the OPERATOR'S OWN ACTIONS in the END-OF-RUN REPORT: a new section naming what the
agent operator seat did — including the acts that were refused or failed, which are the
operator's own misses and must be visible as such.

This is the REPORT-LINE half of v8 step 2's operator seat. The read-only view it reads
(`api.operator_actions`) ALREADY EXISTS ON MAIN (shipped separately, with the ledger table
and the write verb). This slice ONLY renders those rows + wires the fetch. It applies NO
consequence, touches NO auth path, adds NO DB migration — a PURE FORMATTER change plus a
graceful fetch. It is fully SUBSTRATE-FREE to validate (a vitest unit test, no database).

NOTE — this brief is SINGLE-USE: the run ships its task to `main`, so a re-run needs a
fresh brief whose work isn't already on main.

WHY IT MATTERS (context, not work): until v8, "the operator" was not an identity — it was
whoever held the signing key, minting as whichever worker family the act happened to need.
Operator work landed in a worker's history and, through M20, in that worker's track record.
The seat is now its own family (`agent+operator`), and its instance-scoped acts — starting
the service, reconfiguring a tier — have no task, so they cannot be events (app.events.task_id
is NOT NULL). They live in their own append-only ledger. The report is where a human reads
what the seat did without going to the database.

WHAT EXISTS TODAY (read before coding; do NOT change any of it):
- bin/ainarres.mjs exports the PURE `formatReport({ board, timeline, trackRecord, governance,
  auditFlags, governanceActions, spendAnomalies, operationalFlags, openBriefs, stuckTasks },
  { lane })`. Its LAST section is "operational (v6 — health & spend watch):".
- `reportJson(...)` mirrors the same inputs and emits `operational: { … }`.
- The `report` command fetches the views and passes rows in, degrading to [] on error
  (see the `stuck_tasks` / `operational_flags` fetches — copy that shape exactly).
- `fmtTokens`, `fmtHeal` and `fmtDuration` are the model for small pure helpers;
  pure-formatter tests live in test/status-format.test.ts.
- The governance section already renders `governanceActions` (the human ban/lift trail) as
  its own capped list — the closest existing shape to this one.
- `api.operator_actions` — read-only, readable by oversight and monitor, NEWEST FIRST.
  Columns:
    family (text), action (text, a lower_snake slug like 'refine' or 'service_start'),
    target (text, nullable — free text naming what was acted on),
    task_id (uuid, NULLABLE — null for the instance-scoped acts),
    outcome (text: 'ok' | 'refused' | 'failed'),
    reason (text, nullable — why it was refused/failed),
    detail (jsonb object), actor_sub (uuid), created_at (timestamptz)

THE FEATURE — ONE TASK (no DB migration; the view is already on main):

1. Extend `formatReport`'s first argument with `operatorActions = []` (EXACTLY as
   `stuckTasks` was added) and render a NEW section titled

     "operator (v8 — what the seat did):"

   placed AFTER the whole governance section and BEFORE the "operational (v6 …)" section.

2. Section body, from the rows in the order the view returned them (newest first — do NOT
   re-sort), capped at 10:
   - Empty input renders exactly one line: "  (no operator actions)".
   - Otherwise, a COUNT line first:
       "  <N> action(s) · <M> refused/failed"
     where N is the total number of rows PASSED IN (before the cap) and M is how many of
     those have outcome 'refused' or 'failed'. Use the literal word "action(s)".
   - Then one line per row (max 10):
       outcome 'ok':
         "  - <family> <action> <targetPart>"
       outcome 'refused' or 'failed':
         "  - <family> <action> <targetPart> — <outcome>: <reason or "no reason given">"
     where <targetPart> is:
       - `→ <target>`         when target is a non-empty string
       - `→ task <task_id>`   when target is null/empty but task_id is present
       - `(instance)`         when both are absent — the acts that cannot be events
     A null/empty `family` renders as "—" (matching the health line's convention).

3. Mirror it in `reportJson`: add a top-level `operator: { total, failed, actions }` where
   `total` is the pre-cap row count, `failed` counts 'refused' + 'failed', and `actions` is
   `operatorActions.slice(0, 10)` passed through unchanged (the JSON shape stays dumb).

4. Wire the `report` command to fetch `api.operator_actions` (use `?limit=25`, the view is
   already ordered newest-first — no `order=` param) and pass the rows in as
   `operatorActions`. Degrade to [] if the view is absent or the request errors: a substrate
   without the view must still produce a full report.
